# 実験用FIRの生成と予測評価（2026-11-07）

保存済みの500〜1,000 Hz測定3セッションから、各3候補、計9候補の有限長FIRを生成しました。9候補とも設計と再生安全性の検査を通過しました。結果は保存された複素応答からの予測で、実機でのキャンセル効果は未測定です。元の有効率不足と同期信頼度不足は維持し、正式合格へ変更していません。

## 元データと候補の対応

入力は無視対象の`build/practical-audit/hfp-ready-500-1000-session1.json`から`session3.json`です。元の生PCMは存在しないため、波形の再解析はしていません。診断スキーマ2の配列長4,097、周波数刻み48,000/8,192 Hz、測定順L1・R1・L2・R2を検査しました。応答配列の順序L1・L2・R1・R2は、保存処理の実装で確認しています。今後の診断にはレートと応答順も明記します。

|---|---|---:|---:|
| 1 | `f129bb6e8e37038dec9fb6f3161eb4419e6f9d85dbdace07b12906547fc836a7` | 78.82% | 1.324 samples |
| 2 | `1a125cf5f59cdcd7a59addfe1624663c49adcf04ae6f41c7e08e240d614e410d` | 60.00% | 1.480 samples |

全セッションに`PILOT_AMBIGUOUS`と`LEGACY_SYNC_RESIDUAL`があり、`timing.reliable=false`のままです。共通時刻モデルによる暫定応答を使い、左右別のピーク整列や反復位相差を消す整列は行っていません。今回の帯域に対する残差上限は12 samplesです。時刻モデル不成立、時刻段差、異常なクロック比、識別不能なパイロット、PCM異常や経路不一致を含む診断は生成元にできません。

全候補で保存設定の1,025 taps、正則化0.01、最大ブースト6 dB、共通出力−24 dBを使用しました。基準chは中央タップの係数を1、ゲインを0 dBに固定し、補正chだけを設計しています。共通の基準遅延は中央512フレームと分数遅延器16フレームです。ピーク上界の許容値は0.9で、共通音量を下げて成立させる処理はありません。

## 生成結果

「集約」は既存の`trial-power-v1`の重みを使います。反復1→2は反復1だけから設計し、反復2で予測を評価します。逆方向も同様です。交差候補の重みは学習側のSNRから決まり、評価側の低減量による選別はありません。単独反復からは反復性を評価できず、両反復から求めた共通時刻モデルも共有しています。そのため、交差予測を完全独立な検証とは扱いません。

要求帯域は85ビンです。生成には正の重みを持つ設計ビン20個以上を要求し、有効率80%や長い連続区間は条件にしていません。設計対象外を真の応答として補間せず、既存設計器の正則化と帯域外抑制を使います。

## 有限長FIRによる予測

表の各値は「片側比 / 無補正両側比」のdB値です。正値は低減、負値は増音を表します。有限長FIRと共通遅延を含む応答へ、要求帯域内の各ビンに等しいエネルギーを与えています。線形電力を合計してからdBへ変換します。集約候補は設計に使った各反復でも評価するため、交差候補とは区別して読む必要があります。

低SNRビンは左右のいずれかが20 dB未満のビンです。全帯域の計算からは除外せず、信頼度不足を表示します。過去の約10 dBという理想補正予測は、周波数ごとの理想複素比を使い、両反復のSNRやブースト条件で評価ビンを選別していました。今回は実際の有限長FIRと等エネルギー信号を使い、低SNR区間を含む要求帯域全体も評価しています。評価ビン・重み・信号スペクトルが異なるため、数値の差をそのまま性能差とは呼べません。

[候補一覧CSV](analysis/experimental-fir-summary.csv)には係数SHA-256、パラメーター、元判定、全帯域と設計ビンの数値を記録しました。[周波数別CSV](analysis/experimental-fir-predictions.csv)の1,020行には、予測値、低SNRフラグ、設計対象外フラグがあり、使用ビンの分布も確認できます。各候補JSONには使用ビンの番号、連続区間、設計理由、共通時刻モデルも保存します。元診断と候補JSONはローカルの無視対象に置き、公開用CSVには端末名・アドレス・生PCMを含めません。

## 再実行

Androidとオフライン処理は同じcoreの`AutoFirDesigner`を呼びます。Pythonは生成済み結果のCSV化だけを担当します。

```powershell
$env:JAVA_HOME='C:\Program Files\Android\Android Studio1\jbr'
.\gradlew.bat :core:experimentalFir --console=plain
python tools/summarize_experimental.py build/experimental-audit/offline docs/analysis
```

既定の入力は`build/practical-audit/`、出力は`build/experimental-audit/offline/`です。別の場所はGradleプロパティ`-PexperimentInput=...`と`-PexperimentOutput=...`で指定できます。入力ファイルがない場合も`index.json`に不足を記録します。出力名は`session1-aggregate.json`、`session1-repeat1-to-2.json`、`session1-repeat2-to-1.json`の形式で、セッション2・3も同様です。オフライン候補のIDには固定nonceの`offline-v1`を使います。

## Androidでの操作

「フィルタ自動設計」から「実験用FIR」へ進み、最新の診断結果か保存診断JSONを選びます。「実験用候補を作成」で予測と品質不足理由を確認できます。タップ数・正則化・最大ブースト・帯域を変更した生成は別IDで保存します。生成だけでは現在のFIRを変更しません。

「候補を比較測定」は選択済みの係数を固定して測る操作です。現在の端点、共通出力、左右割当を使い、再設計はしません。3ラウンドの片側基準・無補正両側・候補FIRと、前後の暗騒音を記録します。比較結果はMIC録音上の相対電力で、校正SPLではありません。比較条件と下限の定義は[設計書](design.md)に記載しています。

「候補・結果を保存」でJSONを書き出せます。比較前や効果不足の候補でも、安全性を満たせば「手動適用」でFIRスロットへ反映できます。位相・振幅スロット、過去の校正、A/Bは保持し、「手動適用を元に戻す」で適用前の設定へ戻します。再起動やJSON読込後も再利用できますが、過去の比較を現在の検証済み表示へ引き継ぎません。

候補は12個まで、比較履歴は1候補3件までです。上限に達した場合はJSONへ保存して一覧を整理します。自動削除はありません。横置きは操作を左、予測と比較結果を右に配置し、狭い画面ではスクロールできます。停止と取消はスクロール領域の外にあります。

今回の確認範囲は保存データによる予測、合成音響系、音声無効エミュレーターです。実機インストール、音出し、MIC録音、実機での低減・再現性の確認は行っていません。試験件数とAPKの識別情報は[検証記録](validation.md)を参照してください。
